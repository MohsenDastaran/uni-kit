# Adding a UI framework to uni-kit

This is the guide for adding a fourth port beside GPUI, Slint and iced. It
describes the contract the repository actually implements, in the order a reader
has to do the work. The iced port is the worked example: its plan, conventions
and verification log are in [iced-integration.md](iced-integration.md), and the
mistakes this project has already paid for are in [roadmap.md](roadmap.md).

A port is not a translation layer. It is a second first-class source
implementation of the same catalogue, with its own theme, its own gallery and
its own place in the registry. The design authority is the Slint catalogue:
`crates/slint-component/ui/<key>.slint` and
`crates/slint-component/ui/theme.slint` are the complete set, and the component
page `website/component/<key>.md` documents the GPUI usage. When they disagree,
follow Slint — it is the framework that has every component.

There are two shapes a port can take:

| Shape | How it ships | Examples |
| --- | --- | --- |
| Source-shipped | Every component is a file the CLI copies into the application, together with the shared theme. | Slint, iced |
| Crate-shipped | The controls live in a crate the application depends on; the registry only copies composed screens. | GPUI |

A fourth port should normally be source-shipped. GPUI's shape works because the
controls already ship in `gpui-kit`; if a new framework cannot be copied as
source, only the registry section changes (entries become blocks), and the rest
of this guide still applies.

## The route at a glance

| Step | You have finished when | Where |
| --- | --- | --- |
| 1. Crate skeleton | `cargo build` and `cargo build --examples` pass; the native gallery runs and lists its stories. | `crates/<framework>-component/` |
| 2. Theme | The port's theme agrees with `theme.slint`, colour for colour. | `src/components/theme.rs`, `scripts/theme-parity.mjs` |
| 3. First component | One component has a source file, a demo, a thin example and a registry entry; `add <framework> <name>` installs a project that compiles. | `src/components/`, `src/demos/`, `examples/`, `registry/` |
| 4. Gallery | `?story=<key>` shows the component in the browser, and the module is built into `www/dist`. | `src/demos/mod.rs`, `src/wasm.rs`, `www/`, `scripts/` |
| 5. Website | The switch offers the framework, the page panels are cut from the demo, and a live frame loads. | `website/` |
| 6. Blocks (optional) | A block's screen is a demo file plus two fields on `/blocks`. | `src/demos/<name>_block.rs`, `website/src/pages/blocks.astro` |
| 7. Gates | `scripts/check.sh --install` passes, and the component has been seen in light and dark. | `scripts/check.sh` |
| 8. Merge and release | `npx` installs after the merge; the npm package is published if the CLI itself changed. | `registry/`, `main` |

## 1. What a port is

### The crate

Use the iced crate as the template. Its layout is the shape a source-shipped
port ends up with:

```text
crates/iced-component/
  Cargo.toml            package, pinned framework version, [workspace], cdylib + rlib
  Cargo.lock            its own lockfile, not the workspace's
  Makefile              build, check, run, stories, wasm, page, bindgen
  src/lib.rs            components, demos, bridge, and wasm on wasm32
  src/components/       one .rs per registry key, plus the shared theme.rs
  src/components/mod.rs generated by scripts/mod-rs.mjs
  src/components/theme.rs  the design tokens every component reads
  src/demos/            one module per story: the whole application
  src/demos/mod.rs      generated: module list, STORIES, dispatcher
  src/demos/index.rs    the list shown for an unknown story
  src/main.rs           native gallery binary (`iced-gallery`)
  src/wasm.rs           browser entry (`#[wasm_bindgen] pub fn run(story, dark)`)
  src/bridge.rs         the code-icon postMessage bridge
  examples/<name>.rs    a thin `main` that runs the demo
  www/index.html        the static gallery page
  www/dist/             build output; git-ignored
  scripts/mod-rs.mjs    generates both mod.rs files
  scripts/status.mjs    the completeness checklist
  scripts/check.sh      the crate gate
  scripts/theme-parity.mjs  compares theme.rs with theme.slint
  scripts/build-wasm.sh, build-page.sh, check-one.sh
```

The crate is deliberately written in the shape an application ends up with:
`src/components/` is the directory the CLI installs into, not a private source
tree that is transformed on the way out. See
[crates/iced-component/README.md](../crates/iced-component/README.md) for the
component shape and
[iced-integration.md](iced-integration.md#the-gallery) for the gallery layout.

`crates/slint-component/` is the other source-shipped example, and it differs
where its language forces it: components are `ui/<key>.slint`, examples are
`ui/examples/<key>.slint`, the theme is `ui/theme.slint`, and icons are shipped
in `ui/icons/`. Everything the CLI copies is under `ui/`.

### Why the crate has its own workspace

A port must not enter the GPUI Kit workspace. The root `Cargo.toml` excludes
Slint explicitly (`Cargo.toml`: `exclude = ["crates/slint-component"]`), and the
iced crate declares an empty `[workspace]` of its own
([crates/iced-component/Cargo.toml](../crates/iced-component/Cargo.toml#L9-L11);
Slint does the same in
[crates/slint-component/Cargo.toml](../crates/slint-component/Cargo.toml#L9-L10)).
There are four reasons, all of them real here:

- The framework's dependency graph must not enter GPUI's lockfile. Slint's and
  iced's crates are not built when someone runs `cargo build` at the root.
- The port pins its own framework version and has its own `Cargo.lock`. iced is
  pinned to `0.14`; the crate's lockfile resolves a different `wasm-bindgen`
  (0.2.129) from the workspace's (0.2.121).
- The wasm-bindgen CLI must match the module's `wasm-bindgen`, and two versions
  cannot share one binary. iced installs its CLI into `~/.wasm-bindgen-iced`
  (`make install-iced-bindgen`) so it never overwrites the shared one. That is
  also why one bad install once broke the Slint gallery.
- The port is source an application copies, not a dependency it links. Keeping
  it out of the workspace makes that distinction structural instead of a rule
  someone has to remember.

So: create `crates/<framework>-component/`, give it `[workspace]`, do not add
it to the root `members`, and build it with `cargo build --manifest-path
crates/<framework>-component/Cargo.toml` or from inside the directory. Adding it
to the root `exclude` as well is optional and only documentation; iced relies on
the empty `[workspace]` alone.

### The component tree

The tree has three layers, and they have different jobs:

```text
src/components/<module>.rs   the component itself: a builder and a style
src/demos/<module>.rs        the whole application the gallery and page show
examples/<module>.rs         a thin `main` that calls the demo
```

- The component is what an application installs. It is a library file: one
  public builder type, a style type, `From<...> for Element`, and no `main`.
- The demo is the same component exercised as a complete application: state,
  message, update, view, and one section per example on the component page.
- The example is what `cargo run --example <name>` runs. It holds only `fn
  main` and calls `demos::<name>::run(theme)`, because the browser gallery has
  to run the same code. Two copies would drift; see
  [crates/iced-component/examples/button.rs](../crates/iced-component/examples/button.rs)
  and [crates/iced-component/src/demos/button.rs](../crates/iced-component/src/demos/button.rs).

A port that has no browser gallery can keep the whole application in
`examples/`. A port with a gallery cannot: the gallery links the library, so the
application has to live in `src/demos/`.

A source-shipped port ships components; a crate-shipped one ships composed
screens. GPUI's copyable unit is a block under `crates/blocks/src/<name>.rs`,
and the registry entry names that one file ([crates/blocks](../crates/blocks)).
That is why its manifest has three entries rather than seventy-nine.

### The gallery and its story registry

One gallery answers for every component; the page asks for one by name with
`?story=<registry key>`. The registry is the `STORIES` list and the
`demos::run` dispatcher in `src/demos/mod.rs`, both generated by
`scripts/mod-rs.mjs`:

```rust
pub const STORIES: &[&str] = &[
    "button",
    "message-role",
    // ...
];

pub fn run(story: &str, theme: iced::Theme) -> iced::Result {
    match story {
        "button" => button::run(theme),
        "message-role" => message_role::run(theme),
        // ...
        other => index::run(theme, other.to_string()),
    }
}
```

The native binary (`src/main.rs`) and the browser entry (`src/wasm.rs`) both call
`demos::run`, so the frame and `cargo run --bin iced-gallery -- <story>` are the
same program. An unknown story is not an error: `index::run` lists what exists,
which is how a reader discovers the catalogue.

The other two ports solve the same problem differently, and a new port should
pick whichever its framework forces:

- **GPUI** registers stories by hand in
  [crates/story/src/gallery.rs](../crates/story/src/gallery.rs) as
  `StoryContainer::panel::<ButtonStory>(window, cx)`. Story names are PascalCase
  (`AlertDialog`), which is why the website carries a `STORY_TITLES` map in
  [website/src/lib/example-counts.ts](../website/src/lib/example-counts.ts) and
  [website/src/components/ComponentExample.vue](../website/src/components/ComponentExample.vue).
- **Slint** has one page per example. `crates/slint-component/build.rs`
  generates `ui/gallery-catalog.slint` from `ui/examples/*.slint` by finding each
  `export component ...Example`, and `ui/gallery.slint` selects
  `if component == "<slug>"`. A development build can compile one page with
  `SLINT_GALLERY_ONLY=<slug>`, because the whole catalogue is one generated Rust
  file that a single `rustc` cannot compile in a laptop's memory.
- **iced** uses one module for every story, which is the simpler route and the
  one to prefer when the framework can compile the whole catalogue at once.

`scripts/mod-rs.mjs` exists because a hand-written module list is the one file
every batch would edit, and a missing entry means the crate silently does not
compile that component — a failure every other check passes. Its `--check` mode
is part of the gate:

```bash
node crates/iced-component/scripts/mod-rs.mjs           # write both lists
node crates/iced-component/scripts/mod-rs.mjs --check    # fail if stale
```

The generated `src/components/mod.rs` always lists `pub mod theme;` first, then
the components; the demos list is the component list plus the block demos, minus
`index.rs`.

### How the wasm is built and served

`crates/iced-component/scripts/build-wasm.sh` is the whole chain:

```bash
scripts/build-wasm.sh              # debug, for working on a component
scripts/build-wasm.sh --release    # what the site deploys
```

It runs:

```bash
cargo build --manifest-path crates/iced-component/Cargo.toml \
  --target wasm32-unknown-unknown --lib
```

inside `script/guard.sh`, the shared cgroup memory cap. (A single iced `rustc`
peaks above what a 14 GiB laptop can spare while the desktop is running; without
the cap the kernel swaps the session out instead of failing the build.) It then
finds the module at
`crates/iced-component/target/wasm32-unknown-unknown/{debug,release}/iced_component.wasm`
and runs wasm-bindgen into `crates/iced-component/www/dist`:

```bash
wasm-bindgen "$wasm" --out-dir "$out" --target web --no-typescript
```

The CLI is chosen in this order: `$WASM_BINDGEN`, then
`~/.wasm-bindgen-iced/bin/wasm-bindgen` (written by
`make install-iced-bindgen`), then whatever is on `PATH`. The version must match
the module's `wasm-bindgen`; the script prints both versions when the bindings
are refused. Do not replace the shared CLI to fix a mismatch.

`scripts/build-page.sh` copies `www/index.html` into `www/dist`, and
`script/optimize-wasm.sh` runs `wasm-opt` if it is installed, leaving the module
alone if not. The output folder is the page, the bindgen glue and the module —
no bundler:

```text
www/dist/index.html
www/dist/iced_component.js
www/dist/iced_component_bg.wasm
```

`www/dist` is git-ignored. In development the site serves it through
`website/src/lib/wasm-middleware.js`, which maps `/iced-gallery` to
`crates/iced-component/www/dist`; `make dev:website-iced` builds the module and
then starts the site. In production `.github/workflows/release-website.yml`
installs the matching bindgen CLI, runs `make build-wasm`, builds the site, and
copies `www/dist/*` into `website/dist/iced-gallery/`. The frame's URL is
`/iced-gallery?story=<key>`.

The other two ports take different routes to the same place. GPUI builds
`crates/story-web` with the workspace's `wasm-release` profile, a larger link
stack, wasm-bindgen into `www/src/wasm`, and Vite for the page; the site serves
it at `/gallery` (`make build:wasm-gpui`). Slint builds each page into its own
folder (`crates/slint-component/scripts/build.sh`) because each page is a
distinct generated component type. A new port can use the iced route — one
static page, one module, no bundler — or follow whichever of these its front end
needs. The iced route is the simplest and the one to start with.

`www/index.html` resolves the glue from the directory it is mounted at, not from
`./`:

```js
const mounted = location.pathname.replace(/\/+$/, '') + '/';
const { default: init, run } = await import(mounted + 'iced_component.js');
await init();
run(story, dark);
```

`/iced-gallery` is a path with no trailing slash, so a relative `./iced_component.js`
would resolve against the site root. That is exactly how the first version of
the page failed in the browser while the module was being served correctly.

The iced page also reads the host page's palette and reloads the frame when the
host theme changes, because an iced application takes its theme when it starts.
A framework with a live theme API can repaint instead; one without has to
reload, and the page should say so rather than showing a frame that thinks it is
light.

## 2. The first component

Do one component end to end before batching. `button` is the worked example; it
has the variants, sizes, states, groups, progress, dropdown and icon-only
sections the Slint example has, and it proves the whole route: source, demo,
example, registry entry, gallery story, page panels and code icon. The iced
button is the most complete demo, with eleven sections (the Slint ten plus a
live loading state); a simple control such as `badge` or `label` is a better
first file if you want the mechanics before the detail.

Read `crates/slint-component/ui/<key>.slint` first, and only it. It is short and
it is the authority. Then read the component page for the GPUI sample. Do not
start by reading the framework's whole API reference; the iced reference is
over 1,300 lines, and reading it before writing is how a port stalls. Write the file
rough, let the compiler name the one symbol each error needs, and grep the
reference for that symbol.

### The component contract

From [crates/iced-component/README.md](../crates/iced-component/README.md) and
the files it describes, adapted to the general case. (The README predates the
demo split: the application now lives in `src/demos/`, and `examples/` is the
thin `main` described below. The code below is Rust and iced; a non-Rust port
keeps the contract and uses its own module and builder idioms.)

- **One file per registry key.** A key may hold a hyphen (`description-list`);
  a module may not, so the file and the module are the key with hyphens as
  underscores (`description_list.rs`, `pub mod description_list;`). The file's
  module docs name the key it installs as.
- **In a Rust port, `#![allow(dead_code)]`** after the module docs. The file is a
  library that arrived by copy: an application uses part of it and would
  otherwise get a warning for every part it does not use.
- **The theme is `super::theme`, never `crate::theme`, in a Rust port.** The
  installed directory can be moved or renamed, and `super` keeps working. Slint
  reaches its theme as a bare `theme.slint` beside the component. This sibling
  reach is also what makes the registry's closure computable.
- **A builder struct** (`Button::new(label).variant(..).on_press(msg)`) and a
  `From<Control> for Element<'a, Message>`. The framework's own interaction
  model decides what a builder method takes: iced carries the message as a
  value, so `on_press` is `Option<Message>`; a framework with callbacks or a
  mutable widget tree should use its own idiom rather than inventing a iced
  shape.
- **A `Style` type** holding the flags, with `resolve(&self, tokens, status)`
  returning the widget's own style struct. The `From` impl hands the framework
  a closure, so the style is resolved at render time:
  `.style(move |theme, status| style.resolve(Tokens::of(theme), status))`.
- **Every colour comes from the theme at render time**, never from a palette
  captured when the element was built. Text takes the framework's text-style
  hook for the same reason. This is the "build-time token trap": a surface
  resolved from the light table when the element is built is white in the dark
  theme, and no compiler will mention it.
- **Sizes, spacing, radii and font sizes** come from the theme constants; the
  per-size metrics come from `ControlSize` (or the equivalent size enum). Read
  `crates/iced-component/src/components/theme.rs` for the actual scale:
  `SPACING_XXS` through `SPACING_XXL`, `RADIUS_SM` through `RADIUS_XL`,
  `FONT_SIZE_XS` through `FONT_SIZE_XL`, `FONT_SIZE_MONO`, and
  `ControlSize::control_height`/`input_height`.
- **Every interaction state is drawn**: rest, hover, press, disabled, and
  selected where the component has one. `theme::hovered` and `theme::pressed`
  reproduce the Slint theme's HSL shifts. A state that exists but is not drawn
  is a component that looks finished and is not.
- **No `todo!()`, `unimplemented!()`, "not implemented", or "Implementation
  pending"** anywhere. The checklist refuses to count a stub, and a stub is a
  lie the gates cannot see.
- **No colour written by hand in code.** Hex values in comments are fine when
  they record a measurement; `Color::from_rgb` or a literal fill in the drawing
  code is not.

The theme is the one file every component reads, so it is worth getting right
before the second component. It is transcribed from
`crates/slint-component/ui/theme.slint`, which is itself the Slint mapping of
`tokens/tokens.json` (see `tokens/README.md`). The authority chain is:

```text
tokens/tokens.json  ->  crates/slint-component/ui/theme.slint  ->  <framework>/src/components/theme.rs
```

The port's theme has the same names as the Slint theme, with hyphens written as
underscores, so a component reads beside its Slint original. `Tokens::of(theme)`
returns the light or dark table from the framework's current theme, and the
gallery's host-palette path (`set_site_palette`) is what makes an embedded frame
wear the page's palette rather than a hard-coded pair. Not every framework needs
the host-palette half; every port needs the light and dark tables.

### The demo and the `// section:` contract

The demo is a whole application, not a view. In iced terms:

```rust
pub fn run(theme: iced::Theme) -> iced::Result {
    iced::application(boot, update, view)
        .title("uni-kit — button")
        .theme(theme)
        .subscription(subscription)
        .run()
}
```

Its sections are marked with comments, and those comments are a contract with
the website. The reader in
[website/src/lib/remark-iced-source.js](../website/src/lib/remark-iced-source.js)
cuts the demo file into the usage panels a component page shows:

```rust
// section: Variants
let variants = column![ /* ... */ ];
// section: Sizes
let sizes = column![ /* ... */ ];
// section: end
```

Rules that are not optional:

- One `// section: <title>` per documented example, in the order the sections
  appear on the page.
- The title must match the heading the page actually uses. Usually that is the
  page's `###` sample heading, but not always: `bubble.md` documents every
  behaviour as an `##` section. Match the heading the sample is documented
  under, at the depth it uses, and check with the plugin's own extractor rather
  than assuming a depth. A title that is a lookup key, not a label: a section
  named after the page region rather than the heading it documents posts an
  index that finds no scroll target and reads as a dead icon.
- Close the last section with `// section: end`. Without it, the lines that
  assemble the gallery — the status line among them — are shown as part of the
  last sample.
- Keep the sample compilable **as printed**. A marker placed before a function's
  closing brace cuts a sample that cannot compile even though the running demo
  is fine. The dock page shipped one at `+1` brace balance; a brace-balance
  sweep over every demo's sections is worth running.
- Put live controls that are not themselves documented samples after
  `// section: end`: a theme toggle, a status line, a counter. Then changing or
  removing one can never move the page's contract.
- Run it natively before building any wasm:
  `cargo run --bin iced-gallery -- <name>` (or `make run STORY=<name> DARK=1`).

The heading helper is part of the demo, not the component. It draws the section
title and the code icon, and posts through `crate::bridge` on release:

```rust
Message::ShowSource { index, title } => {
    app.pressed_source = None;
    crate::bridge::show(index, title);
}
```

The icon is the same chip the Slint and GPUI galleries draw (`primary` at 0.12
with a 0.35 border; 0.22/0.55 on hover; 0.34/0.7 pressed). The chip is copied
into almost every demo rather than owned in one place, so a change to it is a
change to every demo and to the Slint reference together; do not change it in
one framework alone.

### The example binary

`examples/<module>.rs` is a complete `main` and nothing else:

```rust
//! `button` — a push button, in the variants, sizes and states the catalog
//! shares with GPUI and Slint.
//!
//! The demo itself lives in the library, so the gallery the website embeds
//! shows the same one. Run it with `cargo run --example button`.

fn main() -> iced::Result {
    iced_component::demos::button::run(iced::Theme::Light)
}
```

`cargo build --examples` compiles every example, and that is the gate. The
example is what a reader copies, so it must be an application, not a stub: the
checklist looks for `fn main` plus either the framework's application entry
point or a call to `demos::<name>::run`.

### What "done" means for one component

The generated checklist in `docs/<framework>-integration.md` reads three things
from the tree: a component source, an example, and a registry entry. The iced
checklist's `implemented()` also refuses a stub, and its example test accepts
either a full application or a thin `main` calling the demo. On top of that, the
hand checklist in [roadmap.md](roadmap.md) is the real bar:

- the component uses tokens only, with no colour written by hand;
- the demo runs and has one `// section:` per example;
- the example is a thin `main` that calls the demo;
- the registry entry exists, so `add <framework> <name>` installs it;
- `scripts/check.sh` is green (module lists, both cargo builds, theme parity,
  feature agreement, the manifest);
- every card's code icon scrolls to *its* sample, and the sample shown is the
  source of the example that is running;
- it has been seen in light **and** dark, by looking at a screenshot, not by
  reading tokens;
- it is one commit per component.

## 3. The registry

The registry is generated, not hand-edited. Run:

```bash
node registry/build-manifest.mjs
```

It writes two files:

- `registry/components.json` — the manifest the CLI reads. It has one key per
  framework, each with `default_target_dir`, an optional `mod_file`, and a
  `components` map from registry key to file list.
- `website/src/lib/registry-slugs.json` — the same keys, as sorted string
  arrays, for the site. Do not edit it by hand.

The current top level is `slint`, `egui`, `gpui`, `iced`, `quickgui`; `egui` and
`quickgui` are placeholders with empty component maps. A new framework starts
the same way if you want to reserve the key, but it must not appear in the
website's `FRAMEWORKS` or selector until at least one component is real. The
roadmap's rule is explicit: do not list a framework in the selector before its
source exists.

### An entry, field by field

A current iced entry for `button`:

```json
[
  {
    "src": "crates/iced-component/src/components/button.rs",
    "target": "button.rs",
    "module": "button"
  },
  {
    "src": "crates/iced-component/src/components/theme.rs",
    "target": "theme.rs",
    "module": "theme"
  }
]
```

- `src` is relative to the repository root. The CLI reads it from the checkout
  (`UNI_KIT_ROOT`), the local tree, or raw GitHub at `main`, depending on how it
  is run.
- `target` is relative to the framework's `default_target_dir`. It must not
  contain `..` or be absolute; the CLI refuses such an entry rather than writing
  outside the target directory.
- `module` is what makes the CLI add `pub mod <module>;` to `mod_file`. A file
  with no `module` is copied but not declared — that is right for a `.slint`
  file and wrong for a Rust module.

The framework block itself is shaped like this:

```json
{
  "default_target_dir": "src/components",
  "mod_file": "src/components/mod.rs",
  "components": { "button": [ /* ... */ ] },
  "needs_extra": { "text-view": ["iced_core"] },
  "extra_versions": { "iced_core": "0.14" }
}
```

`needs_extra` and `extra_versions` are how the CLI knows a component reaches for
a crate beyond the framework. They are read from the sources, not listed by
hand: `build-manifest.mjs` scans each component for the crates it knows how to
check (`iced_core` is the current list) and reads the version from the port's
`Cargo.toml`. If a source uses `iced_core` and the manifest does not declare it,
the builder fails rather than writing an install hint that cannot compile.

The Slint entries are the other shape: a closure of `.slint` files and, when the
component reaches `icon.slint`, the whole `icons/` folder. They have no
`module`, because there is no Rust module to declare.

### The sibling-dependency closure

This is the most important part of the registry. A component file is not
self-contained: it reaches its siblings as `super::<module>`, and a copied file
only compiles when those siblings are copied beside it. `build-manifest.mjs`
computes the closure by walking what a file imports until every file it reaches
has been seen:

```js
function closure(start, importsOfFile) {
  const seen = new Set();
  const pending = [start];
  while (pending.length) {
    const file = pending.pop();
    if (seen.has(file)) continue;
    seen.add(file);
    for (const imported of importsOfFile(file)) pending.push(imported);
  }
  return [...seen].sort();
}
```

For iced, `componentImportsOf` strips comments first and then matches
`super::<name>`:

```js
const text = fs.readFileSync(...)
  .replace(/\/\*[\s\S]*?\*\//g, '')
  .replace(/(^|[^:])\/\/[^\n]*/g, '$1');
return [...text.matchAll(/\bsuper::([a-z_][a-z0-9_]*)/g)]
  .map((match) => `${match[1]}.rs`)
  .filter((imported) => imported !== 'theme.rs' && fs.existsSync(...));
```

Three details matter:

- **Comments come out first.** A doc comment such as
  ``[`Button`](super::button)`` links a sibling without depending on it. If the
  closure counted it, every component that merely mentions another would drag
  that file into its install.
- **Only existing files count.** `use super::<item>` inside a file's own test
  module is a Rust path, not a component. The `existsSync` filter keeps it out.
- **The theme is appended once, after the closure**, not counted as a sibling.
  The CLI writes it once however many components are installed, and
  `src/components/mod.rs` declares it once.

Why it must be complete: installing `number-input` used to write
`number_input.rs` and `theme.rs` alone, and the application then failed on a
missing `input.rs` and `button.rs`. The crate compiled — every file was present
in the crate — but the copy did not. The manifest is the only statement of what
a copy has to carry, so an incomplete closure is a broken install that no check
inside the crate can see.

The composition can be large. `date-picker` is a real closure:

```bash
$ UNI_KIT_ROOT=$PWD node registry/index.js add iced date-picker --dir src/components
  src/components/calendar.rs
  src/components/date_picker.rs
  src/components/input.rs
  src/components/popover.rs
  src/components/theme.rs
  ...
```

The same closure is what makes `check.sh --install` meaningful: it installs
every manifest key into its own scratch crate, so a sibling that the manifest
omitted cannot be supplied by another component in the same project.

### The name triple

The same component has one name, and the project calls it the name triple: the
manifest key, the site page slug, and the story name — the latter meaning both
the `STORIES` entry and the `demos::run` arm, which `mod-rs.mjs` writes together.
For `message-role`:

| Place | Value |
| --- | --- |
| File | `crates/iced-component/src/components/message_role.rs` |
| Manifest key | `message-role` |
| Component page | `website/component/message-role.md` |
| Story list | `"message-role"` in `demos::STORIES` |
| Dispatcher | `"message-role" => message_role::run(theme)` |
| Gallery URL | `/iced-gallery?story=message-role` |

`scripts/mod-rs.mjs` generates the last two from the file name, converting
underscores back to hyphens. `build-manifest.mjs` generates the manifest key the
same way and refuses a file whose module name is not a valid Rust identifier, or
two files that map to the same key. The page slug is the file name under
`website/component/`.

There is one deliberate exception, and it is worth understanding before naming a
new port's files. The page slug for the dropdown is `dropdown_button.md`, while
the iced registry key is `dropdown-button`, because the Slint side keys on that
page slug in four places and renaming the page fixes iced by breaking Slint. The
project normalises the **framework-facing** lookups instead:

- `scripts/status.mjs` maps both sides through `moduleOf` (`-` to `_`).
- `ComponentExample.vue`'s `icedRegistryKey` maps the page slug's `_` to `-`.
- `InstallCommand.vue`'s `registryName` tries the framework's own list first and
  then the hyphenated form.
- `example-counts.ts` and `BlocksGallery.vue` use the same rule.

A new port should pick one spelling for its registry keys and one for its page
slugs, and normalise only at the boundary. Do not rename a page to make a new
framework's key match; check every framework that already keys on it first.

### The CLI side

The CLI is `registry/index.js`. It reads the manifest in this order:

1. `UNI_KIT_REGISTRY` — a path or URL override, used by tests and by the
   doctored-manifest check that proves the installer can fail.
2. In a checkout (a directory with a `crates/` beside `registry/`), the local
   `components.json`.
3. Installed, the manifest at
   `https://raw.githubusercontent.com/MohsenDastaran/uni-kit/main/registry/components.json`.
4. The copy bundled in the npm package, as a fallback when the network is
   unavailable.

The source files are read from `UNI_KIT_ROOT` if set, then the local checkout,
then `main` (overridable with `UNI_KIT_RAW`).

For a new framework you add:

- the framework block and its `rust(dir)`-style builder in
  `registry/build-manifest.mjs`, plus its component walk, closure, theme append
  and extra-crate detection;
- the framework's name in `registry/index.js`'s usage text and, if it needs a
  dependency line or an install step, an `ensure<Framework>Dependency`-style
  function called from `main()` (Slint's is `ensureSlintIncludePath`; iced's is
  `ensureIcedDependency`);
- a section in `registry/README.md` saying where the files land and what the
  application has to depend on.

The generic path already handles the rest: validate every name before writing
anything, read every source before writing any of it, write shared files once,
add `pub mod` lines, and tell the application to declare the parent module in
its crate root. The two errors a new port will hit first are:

```text
Framework "<name>" is not in the registry.
Component "<name>" for <framework> is not in the registry yet.
```

The first means the manifest has no such framework key (or the CLI is reading
`main` without your branch); the second means the key exists but has no entry
for that component.

## 4. The gallery

### Registering a story

For the iced/one-module shape:

1. Add `src/demos/<module>.rs` with `pub fn run(theme) -> iced::Result`. It must
   be a whole application, not a view.
2. Run `node scripts/mod-rs.mjs`. It writes `pub mod <module>;`, the
   `"<hyphenated-key>"` entry in `STORIES`, and the dispatcher arm.
3. Run it natively, from `crates/iced-component`: `cargo run --bin iced-gallery
   -- <key>` (or `make run STORY=<key> DARK=1`).
4. Build the page:
   `make -C crates/iced-component build-page` copies `www/index.html` alone;
   `make build:wasm-iced` builds the module; `make dev:website-iced` does both
   and starts the site.

A demo that exists is a demo `?story=` can name, because the dispatcher is
generated from the directory. That is the whole reason `mod.rs` is not
hand-written.

For the Slint/per-page shape, add `ui/examples/<slug>.slint` exporting a
component whose name ends in `Example`; `build.rs` writes the catalogue and the
page folder. `scripts/pages.sh` prints the slugs in the order the catalogue uses;
`scripts/build.sh --out <dir>` and `SLINT_GALLERY_ONLY=<slug>` build one page.

For GPUI, register `StoryContainer::panel::<XStory>` in
`crates/story/src/gallery.rs` and give the story its title in
`crates/story/src/stories/`. The website's `STORY_TITLES` map is for the cases
where the story name is not the title-cased page slug.

### The code-icon bridge

The code icon beside a section, and the section's own title, ask the embedding
page to scroll to the sample. The click has to cross the frame boundary, so the
gallery posts a message:

```json
{"source":"gpui-kit","index":0,"title":"Variants"}
```

The iced bridge is
[crates/iced-component/src/bridge.rs](../crates/iced-component/src/bridge.rs):

- It is wasm-only; natively the call does nothing, so a demo can be clicked
  through without a browser.
- It compares the window with its parent as JavaScript values, so a gallery
  opened in a tab of its own does not post.
- It posts to `parent` with the page's origin, not `*`.
- The payload is assembled by hand, so the title is escaped by `json_string`.

The page's receiver is `onExampleMessage` in
[website/src/components/ComponentExample.vue](../website/src/components/ComponentExample.vue):

- It rejects a different origin.
- It accepts the message only from one of the page's own example frames.
- It accepts a JSON string or an object.
- It checks `payload.source` against a set. iced posts `"gpui-kit"` (the same
  tag the other galleries post); the set also contains `"iced-component"`. A new
  port can reuse the shared tag and change nothing here, or post its own tag and
  add it to the set.
- It calls `showExample(title, index)`, which uses `findExampleHeading` in
  [website/src/lib/example-target.js](../website/src/lib/example-target.js) to
  pick the heading by title, by the framework-only mark, and by the section
  index. The heading the remark plugin tagged with `data-gallery-title` and
  `data-gallery-index` is the one that scrolls.

If the icon does nothing, the usual causes are: the demo's section has no
`heading(...)`, the heading has no `data-gallery-title`, the title does not match
the page heading after normalisation, or the heading is hidden under the active
framework. `findExampleHeading` also prefers a heading whose section belongs to
the framework in force, because several frameworks can share a title.

### Producing the wasm

The whole chain is described in section 1. The gallery-specific commands are:

```bash
make -C crates/iced-component build-page          # page and sources only
make -C crates/iced-component build-wasm          # release module + page
make dev:website-iced                             # module + site
make dev:website-iced-page                        # page + site, no compile
make build:wasm-iced                              # release module for the site
make install:iced-bindgen                         # the CLI the lockfile wants
make clean:iced                                   # remove www/dist
```

The root Makefile's `build:wasms` also names `build:wasm-iced`; add a new port's
target there when it has one.

`www/index.html` reads `?story=` and the host theme, then imports the glue. The
page uses `#loading` as the signal that the application has drawn its first
frame; `ComponentExample.vue` observes it and reveals the frame, with a
120-second boot limit. A new port's page should follow the same contract, or the
site's loader will wait forever.

## 5. The website

Most of the website is data: a framework name in an array and a selector group
in CSS. The genuinely framework-specific parts are the source plugin, the story
frame URL, the example counter and the prompt. Everything else is a list to
extend.

### The switch and its data attributes

The framework in force is `html[data-framework="<name>"]`. It is written before
first paint by the inline script in
[website/src/layouts/BaseLayout.astro](../website/src/layouts/BaseLayout.astro#L132-L157),
from, in order:

1. `?framework=<name>` in the address bar;
2. `localStorage['selected-framework']`;
3. the default, `slint`.

The page's switch is
[website/src/lib/framework-switch.ts](../website/src/lib/framework-switch.ts).
It holds `FRAMEWORKS`, `DEFAULT_FRAMEWORK`, the storage key and the query
parameter. It:

- sets `data-selected` on `.framework-switch` / `[data-framework-select]` and
  `aria-checked`/`aria-selected` on `[data-framework-option]`;
- announces the new framework through `[data-framework-status]` and the bar's
  `data-status-<name>` attributes (read in the script as `dataset.status<Name>`);
- writes the query parameter (leaving it out for the default) and rewrites
  `a[href^="/"]` links so the choice survives a click;
- redirects a reader to `data-framework-fallback` when the page's
  `data-framework-available` does not contain the chosen framework;
- dispatches `framework-change`, which the ToC, the sidebar and the blocks
  gallery listen for.

The data attributes a new framework has to join:

| Attribute | Set on | Meaning |
| --- | --- | --- |
| `data-framework` | `<html>` | The active framework. |
| `data-framework-option` | switch buttons | One option in a switch. |
| `data-selected` | switch group | The selected option (written by the script). |
| `data-framework-status` / `data-status-<name>` | framework bar | The screen-reader announcement. |
| `data-framework-available` | `.doc-content`, sidebar rows | Space-separated frameworks this page/row has a view in. |
| `data-framework-fallback` | `.doc-content` | Where to send a reader when the page lacks the chosen framework. |
| `data-framework-code` | a code group | One copyable sample with a panel per framework. |
| `data-framework-panel` | a panel | The framework's version of that sample. |
| `data-framework-only` | a section/heading/block | This content belongs to one framework only. |
| `data-framework-missing` | a section/heading/group | These frameworks have no sample in this section. |
| `data-framework-count` | sidebar count | The examples this framework's window paints. |
| `data-framework-support` | footer tile | The support tile for a framework. |
| `data-framework-link` | nav link | A link scoped to one framework. |
| `data-gallery-title` / `data-gallery-index` | a page heading | The sample a gallery card can scroll to. |

The selector itself is
[website/src/components/FrameworkSelect.astro](../website/src/components/FrameworkSelect.astro).
Add an option to both the trigger's value list and the menu, with a
`data-framework-value` and `data-framework-option`, and add the corresponding
lines to its `<style>` — the file lists the frameworks in three selector groups
(trigger label, selected option, check mark). Its hint is a two-framework nudge:
the current CSS shows "Try GPUI" for every non-GPUI framework and "Try Slint"
for GPUI, so a reader on a fourth framework still sees GPUI. That does not
break, but decide whether the hint should name the new framework instead.

The switch CSS in [website/src/styles/global.css](../website/src/styles/global.css)
also names the frameworks in the `.framework-switch` and `.framework-select`
groups. Grep for `data-framework` and add a line to each group; a selector group
that lists three frameworks and gets a fourth option without a matching rule
leaves that option unstyled, which is easy to miss because the page still works.

### The per-framework panels

[website/src/lib/rehype-framework-code.js](../website/src/lib/rehype-framework-code.js)
is the other half of the page's code. The remark plugins insert fences; this one
groups them so the page can show one framework at a time:

- It visits every `<pre>` on a component page. A block's framework comes from
  its `data-language` (`slint` or `iced`); anything else is the GPUI block the
  page was written around.
- The first block of a run creates a `.framework-code` group with one
  `data-framework-panel` per entry in `FRAMEWORKS`. A later block of a framework
  that has not spoken yet joins that group, provided only blank nodes sit
  between them.
- A framework with no block in a group gets a missing note — except iced, whose
  panel is left empty and shown as nothing. An empty panel is what tells
  `panelAbsent` that the framework has no sample here, so the whole section can
  be hidden in that view; a missing note says the same thing more loudly.
- `markSingleFramework` marks a group that has only one framework's sample with
  `data-framework-only`; `hideAbsentSections` marks the heading and prose around
  a group when the *whole section* has no sample for a framework.
- The stylesheet shows only the active framework's panel
  (`html[data-framework="<name>"] .framework-code__panel[data-framework-panel="<name>"]`)
  and hides `data-framework-missing` / `data-framework-only` for the others.

A new port adds itself to `FRAMEWORKS` and `NAMES`, teaches `frameworkOf` its
fence language (or sets `data-gallery-framework` on the code node), and makes
its remark plugin emit `lang: '<framework>'` — aliased for Shiki in
`markdown.js`. The grouping itself is generic. Choose "missing note" or "empty
panel" deliberately, and keep it consistent: the empty panel is what makes a
section disappear cleanly under a framework that has nothing there.

### The per-framework source plugin

The page's iced panels are written by
[website/src/lib/remark-iced-source.js](../website/src/lib/remark-iced-source.js),
and it is the file to copy for a new framework. Its public surface is:

- `has<Framework>Example(slug)` — whether `examples/<module>.rs` is a real
  application, not a stub or a comment-only file;
- `has<Framework>Component(slug)` — whether `src/components/<module>.rs` builds
  an `Element`;
- `has<Framework>Page(slug, example)` — both of the above and the page is not
  `example: false`;
- `<framework>Sections(slug)` — the `// section:` cut;
- `remark<Framework>Source()` — the plugin.

The plugin's job, in order:

1. Find the page slug from the markdown file path (`component/<slug>.md`).
2. Return early if the page has no real example.
3. Read `src/demos/<module>.rs` and cut it at `// section:` markers, de-indenting
   each block by its smallest indent and trimming blank lines.
4. Inject the demo's `use` lines under the page's `## Import` heading, so a
   reader who chose this framework sees the imports they would actually write.
5. For each section, find the page heading whose text matches the title after
   normalising case and punctuation. Tag it with `data-gallery-title` and
   `data-gallery-index`, and insert the code fence under it.
6. If the heading is already claimed by an earlier section with the same title,
   create a new heading after the page's own sample, with a `— n of m` subtitle
   and `data-framework-only`.
7. If the page has no heading for the section, create one under the end of
   `## Usage` (or before `## API Reference` when there is no `## Usage`), mark it
   `data-framework-only`, and insert the sample under it.
8. Use a fence language the highlighter knows. iced uses `lang: 'iced'`, aliased
   to `rust` in `website/src/lib/markdown.js`, because a language Shiki does not
   know loses the whole block. A `data-*` property set on the code node does
   **not** survive the trip to HTML; the language does.

The plugin's `has<Framework>Page` is the same question the sidebar and the switch
ask, so it must be cheap and honest: an example that is a stub or absent answers
no, and a page with `example: false` answers no. That is what keeps the site from
claiming a framework it does not have.

`component-loader.ts` has a separate cache: the component pages are rendered
once and cached by markdown digest, and a change in a demo would otherwise stay
invisible. Add the new sample directory and extension to its `sampleSources`
list, or a demo edit will not re-render the page in development.

### The sidebar, counts and availability

`website/src/lib/sidebar.ts` is where a page's framework list is computed.
`pageFrameworks(slug, example)` always starts with `gpui` (every page is a GPUI
page) and adds the others:

```ts
function pageFrameworks(slug, example) {
  const frameworks = ['gpui'];
  if (!exampleSourcesAvailable || hasSlintPage(slug, example)) frameworks.push('slint');
  if (!icedExampleSourcesAvailable || hasIcedPage(slug, example)) frameworks.push('iced');
  return frameworks.join(' ');
}
```

A missing source tree must mean "unknown", never "missing": if the directory is
not on disk, the framework stays in the list rather than emptying the whole
navigation. A new port adds the same guard for its own source directory.

The value is used three ways:

- `ComponentExample.vue` gets a `frameworks` prop and marks the framework
  unavailable — the frame shows its missing note instead of another framework's
  code — when the page does not have it;
- `[...slug].astro` writes `data-framework-available` and
  `data-framework-fallback` on `.doc-content`;
- `ComponentPageFooter.astro` builds the support tiles from the same string.

`moduleOf`-style normalisation belongs here too. The page slug is the page's own
name; the registry key may not be. Do not make the sidebar or the switch learn a
second spelling per framework — normalise once at the boundary.

`example-counts.ts` counts the examples each framework's window paints. Add:

- a key to `GalleryCounts`;
- an availability flag (`icedExampleSourcesAvailable` is the model);
- a `count<Framework>(slug)` that returns 0 when there is no real example, and
  otherwise the number of sections the source plugin reads;
- the `galleryCounts` guard (`if (!gpui && !slint && !iced)`), which must
  include the new count.

The counts are what the sidebar prints and what the hero totals sum. A count of
zero from a missing source tree is not the same as a component with no examples;
the availability flag is what tells them apart.

### The live example frame

`ComponentExample.vue` holds a `frameworkList` entry per framework:

```ts
interface Framework {
  name: string;      // "Iced"
  live: string;      // "Rust & iced"
  library: string;   // "iced-component"
  src: () => string | undefined; // the gallery URL for this page
}
```

For a new framework add an entry whose `src` is the gallery URL for the page's
component, using the framework's own naming rule. The iced entry is:

```ts
`${base}/iced-gallery?story=${encodeURIComponent(icedRegistryKey(component.value))}`
```

The frame:

- mounts when it is the active framework and the page has it, and stays mounted
  once loaded, so switching back is instant;
- uses `#loading` as the boot signal and a 120-second limit;
- loads its size from `props.sizes`, keyed by the URL without its query;
- reads `document.documentElement.dataset.framework` in setup, not in
  `onMounted`, because the production guard watches `available` and acts on its
  first value;
- sends a reader to the catalog when the page has no view in the active
  framework (production only).

The prompt builder (`buildPrompt`) and the install command are the other
framework-specific pieces: `installedFile` knows `ui/components/<slug>.slint`
and `src/components/<slug with - as _>.rs`; a new framework needs its own path
and its own "what to install" text. `pathsIn` currently has a Slint branch and a
GPUI branch; add the new framework's icon or asset syntax if it has one.

### The support tiles and the ToC

The "See this component in other frameworks" tiles are in
[website/src/components/ComponentPageFooter.astro](../website/src/components/ComponentPageFooter.astro).
They are data: `NAMES` gives the display name, `toggleLogos` gives the mark, and
a missing mark gets a lettermark rather than dropping the tile. The tile links
with `?framework=<key>`, a query-only link, which is deliberate: the switch's URL
sync only rewrites `a[href^="/"]`, so a query-only link keeps the framework it
names instead of being given the one in force.

The footer's previous/next pair is rendered once per framework and hidden by
`data-framework-only`. `[...slug].astro` builds `pagers` from `FRAMEWORKS` and
`componentNeighbours(sidebar, pathname, framework)`, which skips a page with no
view in that framework. Adding the key to `FRAMEWORKS` is what makes the pair
appear.

The ToC has no framework names in it. `toc.ts` derives the outline from the
headings that are actually laid out (`getClientRects()`), and
`AnimatedToc.vue` refreshes on `framework-change`. It relies on
`data-framework-missing` being correct; if a created iced-style heading lacks
`data-framework-only`, the ToC will list a heading that is hidden under the
active framework. The two closing sections carry `data-toc-trailing`, which ends
the Usage region even on a page with no `## API Reference`.

### The blocks page

`/blocks` is one Astro page, `website/src/pages/blocks.astro`, whose
`definitions` array feeds a Vue island. A framework appears for a block only
when that block declares its fields:

| Framework | Fields on the block | What they mean |
| --- | --- | --- |
| GPUI | `gpuiInstall: ["sidebar"]` | The block file the registry copies. |
| Slint | `slug`, `components`, `slintExample` | The page folder, the controls the install names, which composition to show. |
| iced | `icedStory: "sidebar-block"`, `icedInstall: [...]` | The gallery story and the controls the install names. |

That is the whole contract for a new framework's blocks: add the fields, a
reader for the source, and a branch in `BlocksGallery.vue`'s `visible` and
`srcFor`. The iced reader is `icedBlock(story)`, which reads
`crates/iced-component/src/demos/<story with - -> _>.rs`; the sizes object adds
`iced-gallery` when any block has an `icedStory`.

A block is a whole application screen, not a component demo. Its story name must
not collide with the component demo's: `settings-block`, not `settings`. That is
what lets the same gallery serve both.

For iced the whole contract is:

1. add `src/demos/<name>_block.rs` with `pub fn run(theme)` and a `//!` header;
2. run `scripts/mod-rs.mjs` so the story enters `STORIES` and the dispatcher;
3. add `icedStory` and `icedInstall` to that block's entry in `blocks.astro`.

The install bar, the loader size, the prompt's source and the routing all follow
from those two fields. Omit them and the block simply has no iced view; it is not
an error.

### The hero totals

The home page prints `componentCount` and `exampleCount` from
`catalogTotals()` in [website/src/lib/sidebar.ts](../website/src/lib/sidebar.ts).
The totals are derived from the same page list the sidebar and the pager walk:

- components: one per framework the page has a view in
  (`frameworkAvailable` split and counted);
- examples: the sum of the page's per-framework example counts.

Do not add a literal. The first version printed "158 components" by adding the
manifest's per-framework blocks, which undercounted GPUI badly and was not the
site's component total at all. The invariant that matters is that removing a
page moves the totals by its own share, not by one. Add the new framework to
`pageFrameworks` and to `example-counts.ts`, and the hero follows without an
edit.

## 6. The gates

### `scripts/check.sh`

The crate gate is
[crates/iced-component/scripts/check.sh](../crates/iced-component/scripts/check.sh).
It runs, in order:

```bash
node crates/iced-component/scripts/mod-rs.mjs --check
cargo build --quiet --manifest-path crates/iced-component/Cargo.toml
cargo build --quiet --examples --manifest-path crates/iced-component/Cargo.toml
node crates/iced-component/scripts/theme-parity.mjs
# compare the crate's feature list with the install hint's ICED_FEATURES
node registry/build-manifest.mjs
node crates/iced-component/scripts/status.mjs --check
```

The script does not use `set -e`; it runs every step, reports `FAIL` for each
failure, and exits 1 at the end. That is deliberate: one run tells you everything
that is wrong, not just the first thing.

At the time of writing the step that fails is the checklist, at 76 / 79: `root`,
`theme` and `title-bar` have no source + example + registry entry. `theme` is the
shared theme file (it has a source but no demo and no installable entry), and
`root`/`title-bar` are GPUI concepts. The checklist is honest about that, and
`check.sh` is red because the port is not complete — it is not a false alarm.
Do not copy a red gate as the definition of done.

The `--install` form adds the install sweep. It is opt-in because it compiles
every component against a fresh project:

```bash
crates/iced-component/scripts/check.sh --install
```

What each failure means:

| Failure | What it means | What to do |
| --- | --- | --- |
| `src/components/mod.rs is stale` | A file is not declared, so the crate silently does not compile it. | `node scripts/mod-rs.mjs` |
| `cargo build` | A component or the gallery does not compile, or warns. | Fix it; a warning in an installed file is a warning in a user's project. |
| `cargo build --examples` | An example is missing, is a stub, or does not call its demo. | Write the thin `main`; the example must be an application. |
| `theme.rs and theme.slint disagree` | A colour token has drifted. | Fix `theme.rs`; change `theme.slint` only if the authority is wrong, and then move every port. |
| `crate has [...] and the install hint says [...]` | The feature list and `registry/index.js` disagree. | Update both; hyphens are part of a feature name. |
| `manifest builder` | An entry names a missing file, an invalid module, or a duplicate key. | Fix `build-manifest.mjs` or the source tree. |
| `components are missing` | The checklist found a source/example/registry gap or a stub. | `node scripts/status.mjs` prints the list. |
| install sweep | The closure is incomplete, or the installed source does not compile against the declared dependency line. | Add the sibling/crate; read the compiler error the script prints. |

`scripts/check-one.sh` is not the gate. It copies only the demo's direct imports
into a scratch crate, so it cannot build a *composed* component such as
`date_picker`, `toolbar` or `sidebar`; it fails for reasons that have nothing to
do with the work. The install sweep is the check that covers composition.

### Theme parity against the Slint authority

`crates/iced-component/scripts/theme-parity.mjs` compares the port's `theme.rs`
with `crates/slint-component/ui/theme.slint`. It reads every
`out property <color> <name>: <expression>` from the Slint file, converts the
name's hyphens to underscores, and compares the light and dark channels with the
`LIGHT` and `DARK` tables in `theme.rs`.

Three things are deliberately out of the comparison:

- `in-out property` palette slots. Those are the gallery's host-palette
  overrides, which iced does not have in the same form.
- Completely derived colours, which are listed by name and checked by hand (the
  current run classifies `input_background`, `danger` and `description_label`
  this way).
- `rgba` tokens, which carry alpha; the script skips their channel comparison.

It exits 1 on any mismatch or on a token that is present in one file and not
the other. Run it alone:

```bash
node crates/iced-component/scripts/theme-parity.mjs
```

A green run ends with:

```text
the two themes agree, colour for colour
```

A new port copies this script, changes the two paths (or adds a target
argument), and keeps the same reading: the Slint theme is the authority, not the
port's idea of the palette.

### The completeness checklist

`crates/iced-component/scripts/status.mjs` generates the table in
`docs/iced-integration.md` and is the checklist gate:

```bash
node crates/iced-component/scripts/status.mjs            # print the table
node crates/iced-component/scripts/status.mjs --check    # fail while anything is missing
node crates/iced-component/scripts/status.mjs --write    # write into the doc
```

Its inventory is `registry.slint.components` — Slint is the framework that lists
every component as copyable source, so its keys are the authoritative set. For
each key it reports:

- `source` — `src/components/<module>.rs` is an implementation, not a stub:
  no `todo!`, `unimplemented!`, "not implemented" or "Implementation pending";
  it has a `pub fn`; and it builds an `Element` (or is `theme.rs`, which is the
  shared token file and builds no widget).
- `example` — `examples/<module>.rs` has a `fn main` and either the framework's
  application entry point or a call to `demos::<name>::run`.
- `wired` — `registry.<framework>.components` has the module-mapped key.
- `lines` — the source file's line count, which is how a stub is noticed.

It also counts a file with no implementation but a non-zero line count as a
stub and names it. The table is written between `<!-- iced-checklist:start -->`
and `<!-- iced-checklist:end -->`; a new port creates its own
`docs/<framework>-integration.md` with its own markers and changes the script's
`doc` path, its `ui`/`examples` paths, and its `registry.<framework>` reference.

The checklist is coverage against Slint, not a demand to fake what a framework
does not have. If a key genuinely cannot exist in the port — the shared `theme`
is the current example — the honest options are to leave it red and say so, or
to add an explicit exemption to the script. A stub is the one option that is
worse than an absent component.

### The install sweep

The sweep is the check that the registry, the CLI, the closure and the
dependency line agree. It installs **every** manifest key, each into its own
scratch project:

```bash
crates/iced-component/scripts/check.sh --install
```

For each component it:

1. makes a temporary directory and `cargo new --bin app`;
2. `cargo add <framework> --features <the agreed list> --offline`;
3. adds the component's `needs_extra` crates at the recorded versions;
4. runs `UNI_KIT_ROOT=<repo> node <repo>/registry/index.js add <framework> <component>`;
5. writes `mod components; fn main() {}` so the installed module is compiled;
6. runs `cargo build` with `CARGO_TARGET_DIR` shared with the crate, so the
   framework compiles once.

Each component gets its own project on purpose. Installing the whole family into
one project would let `input` supply the file `number-input` is supposed to
carry, which is the hole the sweep exists to find. It has been shown to fail:
feeding a doctored manifest through `UNI_KIT_REGISTRY` with `input.rs` removed
from `command`'s entry produced `error[E0432]: unresolved import super::input`,
and restoring it made the sweep pass again. A gate nobody has seen fail is a
gate nobody can trust.

The sweep is also the cheapest end-to-end check of the CLI and the shared theme:
it does exactly what a reader does, with only the files the manifest names.

## 7. The traps

These are the ones that cost real time in this repository. A new port will meet
them in its own framework's shape; the mechanism is usually the same.

| Trap | What it looks like, and the fix |
| --- | --- |
| The font set lacks glyphs and has no italic face | The wasm face has no `⌘`, `⌥` or `⇥`, and no italic; a missing glyph paints as nothing (`⌘N` reads as `N`), and an italic span aborts with `no default font found`. Embed a face, enable fallback, and spell the absent marks. |
| `currentColor` resolves to black inside a button | An SVG inside a coloured control paints black whatever `text_color` says. Tint it in the SVG's own style closure (`color: Some(tokens.foreground)`); never inherit. |
| An overlay's host is `layout.position() + translation` | Subtract the translation and the panel lands twice the scroll offset below its trigger. Test an overlay scrolled past the first screen, not at rest. |
| The caret is the text bounds | Deep padding cuts the glyphs; shallow padding gives a full-height caret. Derive `inset_y` from the line (`font * 1.25`) and set `line_height(height - 2 * inset_y)`. |
| Animation needs a redraw requested while it moves | No interval subscription is not no clock: sample the frame's `Instant` and call `request_redraw()` while moving, or `request_redraw_at(deadline)` for one wake-up. |
| `Shrink` / `Fill` axis traps, and a border reserves no room | A `Fill` child in a `Shrink` cross axis lays out at 0; a `Shrink` row in a `Fixed` frame sits at the top; a border is drawn on the bounds, so a filling child covers it. |
| The scroll owner owns the frame; the content owns its padding | An inset around a `Scrollable` is drawn through by the bar and the content. Give the scroll owner the frame and put the padding inside it. |
| A component doc saying the framework "cannot" | It has been wrong six times. Treat "cannot" as a hypothesis and test it in a scratch copy before designing around it. |

A few more that are cheap to name and expensive to rediscover:

- `mix(a, b, t)` weights its **second** argument. `mix(ink, background, 0.04)`
  is 96% ink, which made an alert's title and fill 1.03:1 in both themes.
- `anchor_bottom()` on a scrollable reports **0 as the newest content and 1 as
  the top**, the inverse of the start-anchored fraction.
- `align_bottom(h)` **sets the height** to `h`; it does not align a child to the
  bottom of a taller container.
- `keyboard::listen` sees only *ignored* events. A focused text field swallows
  Escape and the shortcuts, so a binding that "does nothing" may be on the wrong
  listener; `event::listen_with` sees the event regardless of who handled it.
- `Stack` sizes itself from its first child, so a layer meant to cover a frame
  needs `Fill` on both axes.
- A `Canvas` can draw nothing in some positions, and it smears when the region
  around it animates; prefer a widget that draws quads.

### Website traps

- `FRAMEWORK_MARK` in `rehype-framework-code.js` is
  `/framework:\s*(gpui|slint)/`. A `<!-- framework: iced -->` marker matches
  nothing: no mark, no warning, no visible difference. Adding a framework to
  `FRAMEWORKS` is not enough; the regex over the set is what needs changing.
- `data-*` properties are camel-cased on the way into hast. A `data-*` property
  set on a code node does **not** survive the trip to HTML; the fence language
  does. That is why the iced samples are `lang: 'iced'` and not a data attribute.
- A framework in `FRAMEWORKS` needs everything the switch asks for. A
  `key in NAMES && key in toggleLogos` guard silently dropped every framework
  without a logo; `logoElement` now returns nothing for a missing mark and the
  footer falls back to a lettermark. When a set gains a member, change the check
  over the set, not only the data.
- An `in`-style test against a fixed list fails silently by construction. Grep
  for the existing names; the compiler will not find the fourth place.

## 8. Publishing

There are two different events, and the difference matters:

| Event | What it publishes | What works after it |
| --- | --- | --- |
| Merged to `main` | The manifest and the source files on `main`. | The CLI's installed copy reads the manifest from `main` and the sources from `main`, so `npx @dastaran/uni-kit@latest add <framework> <component>` starts working. |
| Released (`npm publish`) | The npm package: `index.js`, `components.json`, `README.md`. | The bundled fallback, and any change to the CLI's own code (help text, dependency hint, framework-specific install step). |

The CLI reads the manifest from
`https://raw.githubusercontent.com/MohsenDastaran/uni-kit/main/registry/components.json`
and the sources from `main` as well. The `components.json` inside the npm
package is only the offline fallback. That is why the iced work can be complete
on a branch and still fail from `npx`:

```text
Framework "iced" is not in the registry.
```

`main`'s manifest has no `iced` key until the branch merges. Merging is what
fixes it; the npm publish is the release process's own step, not a prerequisite
for the manifest. The current README says this in the iced section, and a new
port should carry the same warning until it is merged.

For a new framework the sequence is:

1. Land the crate, the manifest and the website plumbing on `main` (through a
   PR, on a branch, not by publishing from the branch).
2. If `registry/index.js` changed — and it will, for the help text and the
   dependency hint — bump `registry/package.json` and publish:

   ```bash
   cd registry
   npm publish
   ```

3. Verify from a clean directory, after the merge and publish:

   ```bash
   npx @dastaran/uni-kit@latest add <framework> <component>
   ```

   A literal install command on the site is a claim about npm, and it is only
   true after a publish. Check it in a clean project, not in the checkout.
4. If the site's install bar says `@latest`, the command must work with the
   published package. A development branch with a working local CLI is not
   evidence.

`registry/package.json` ships only `index.js`, `components.json` and
`README.md`; the component sources are fetched from GitHub, not bundled. That is
why adding a component needs no release, while changing the CLI does.
